# Development Log / 开发日志

> 说明：本文件是对开发过程的回顾性整理。项目早期没有持续使用 Git，Git 提交历史从 2026-09-01 正式整理进入 GitHub 时才开始记录；本文档如实记录各阶段的开发内容、遇到的问题与处理过程，不伪造过去的 commit，也不为早期开发编造具体日期。

## 1. 项目起点

学生会办公室 908 的日常管理长期依赖人工登记，物资借还和人员值班两类信息记录分散，查询、统计都不方便，也容易出现遗漏。

于是决定做一套小程序 + 后端的管理系统，把物资和值班管理流程电子化。当时的核心需求有三块：

- 物资管理：登记、库存、借用、归还
- 值班管理：排班、打卡
- 权限管理：管理员与工作人员

技术选型上没有用现成的低代码方案：

- 前端：微信小程序（原生 WXML / WXSS / JavaScript）——办公室成员日常都在微信里，小程序打开即用，不需要额外安装
- 后端：Node.js + Express——和前端同为 JavaScript 技术栈，上手成本低
- 数据库：SQLite（better-sqlite3）——数据量是办公室级别的，单文件数据库足够，也省去单独维护数据库服务的负担

运行环境方面，开发联调阶段后端主要跑在本地，曾通过 SSH 隧道让小程序联调到本地服务；生产环境采用 Linux + Node.js + PM2 进程管理 + HTTPS 反向代理对外提供 API。

项目早期没有使用版本控制，开发时间线只能通过工作区文件的修改时间等间接痕迹大致还原（主要页面代码集中形成于 2026 年 7 月上旬）。这也是后面「开发中遇到的问题」里的一条教训。

## 2. 第一阶段：基础项目结构

这一阶段的目标很朴素：让最基本的前后端链路先跑起来。

小程序端搭起了标准骨架：

- `app.js`：启动时检查本地登录态，有 Token 则向后端校验一次，无效就退回登录页
- `app.json`：注册 5 个页面（首页、物资、值班、用户、登录），配置 3 个 tabBar（首页 / 物资 / 值班）
- `app.wxss`：全局样式
- `pages/`：各功能页面
- `utils/api.js`：统一的请求封装——BASE_URL 配置、自动携带 Token、401 自动清理登录态并跳回登录页
- `utils/auth.js`：登录态工具——token / 当前用户的存取、角色判断、登录守卫

后端搭起了 Express 服务：

- `server.js`：入口文件，加载环境变量、注册全局鉴权中间件和各路由模块，提供 `/api/health` 健康检查
- `db.js`：SQLite 连接（WAL 模式、外键约束）、建表、演示数据种子
- `routes/`：按业务拆分的路由模块（auth / users / materials / borrow / duty / checkin）

两端约定 REST 风格接口、统一返回 `{ code, message, data }` 结构。到这一步，健康检查、登录、物资列表这样的基本链路已经可以打通，后续功能都在这个骨架上加。

## 3. 第二阶段：登录与用户系统

用户系统是整个项目最关键的部分之一，因为它决定了谁能用什么功能。

流程是标准的微信登录链路：小程序端 `wx.login` 拿到临时 code → 后端调用微信 `code2Session` 接口换取 openid → 根据 openid 查询或创建 users 记录 → 登录成功时服务端用随机数生成 Token（crypto 随机 32 字节），写入 sessions 表，7 天有效期，返回给客户端。

之后客户端每次请求在 Authorization 头携带 Token，后端全局中间件解析 Token、校验 session 未过期、查出用户注入到 `req.user`。除了健康检查和登录接口外，所有接口都要求有效登录态，未登录返回 401。

用户体系有几个要点：

- 角色：工作人员（staff）/ 管理员（admin）
- 状态：新用户默认 pending，等待管理员审核；审核通过后 active 才能正常使用；disabled 账号无法使用
- 管理员判定早期靠客户端提交的角色标记，后来改为服务端基于 session 中的角色判断——客户端字段不再作为信任来源
- 管理员 OpenID 通过环境变量白名单 `ADMIN_OPENIDS` 配置，未配置时没有管理员
- 管理员写操作（物资 / 值班 / 打卡的增删改、借还批注、用户管理）在后端统一强制校验，staff 越权返回 403

另外有一段真实的演进：早期曾尝试设计独立的身份绑定页面，用来处理「绑定码换身份」之类的场景。后来登录 + 审核的流程定型，这个页面不再参与任何业务流程，而且它没有有效的导航入口，还调用了已经不存在的 API 方法。GitHub 发布整理时确认它属于死代码，最终在发布版中移除，页面注册与实际文件保持一致。这属于流程演进的自然结果，不是某一次故障修复。

## 4. 第三阶段：物资管理

物资管理从简单的库存登记起步，逐渐扩展成完整的借还闭环。

**物资台账**（materials 表）：

- 新增：编号唯一性校验
- 编辑：总量、可借数量、状态等字段的合法性校验（可借数量不能小于 0、不能大于总量）
- 停用：软删除，保留历史数据
- 状态机：可借用 / 已借完 / 损坏 / 停用
- 数据一致性规则：不可借状态一律强制可借数量为 0——这条规则前端表单和后端接口都执行，避免出现「损坏 + 可借 1」这种矛盾数据

**借还记录**（borrow_records 表）：

- 借用：事务内写入借还记录并同步扣减库存；借用前校验物资存在、非损坏、有库存、数量足够；借完自动把物资状态改为「已借完」
- 归还：事务内更新记录状态并恢复库存；校验归还后不超过总库存
- 记录查询：全部记录、未归还列表、最近记录、未归还统计
- 备注字段：借用用途（purpose）、借用备注（borrow_note）、归还备注（return_note）
- 管理员批注（admin_comment）：管理员可以在借还记录上留批注，PATCH 接口且仅管理员可调

借和还都用数据库事务保证「记录」和「库存」两边同时生效，不会出现只写了一边的中间状态。

## 5. 第四阶段：值班与签到

值班模块和物资模块结构类似，但多了一道「打卡」的闭环。

**值班排班**（duty_schedules 表）：

- 新增、编辑、软删除
- 日期规范化：接受 YYYY-M-D、YYYY.M.D、YYYY/M/D 等写法，统一保存为 YYYY-MM-DD
- 本周值班查询与统计

**打卡**（checkins 表）：

- 打卡前校验：值班安排存在、同一人同一值班不能重复打卡、打卡人必须与值班安排中的值班人员一致
- 打卡记录查询、统计；删除为软删除且仅管理员可操作

schema 方面有一段历史：duty_schedules 的 `status` 字段是后期为支持状态记录和软删除补进 schema 的——历史数据里可能存在没有该字段值的行，所以查询语句一直保留着 `status IS NULL OR status != '已删除'` 这样的兼容写法。checkins 表同样用 `status` 字段表示打卡状态，删除为软删除（status 置为已删除）。

## 6. 第五阶段：数据库结构调整

这是 GitHub 发布整理过程中发现并处理的一个真实问题。

长期开发中，db.js 里的初始化建表语句和路由代码的演进并不同步：旧数据库因为字段是陆续补上去的，一直能正常跑；但如果拿初始化脚本在一个全新的数据库上执行，建出来的表会缺少当前路由代码实际在读写的一些字段。

发布整理时对照当前路由的实际查询和写入，逐列核对了初始化 schema，补齐了这些字段：

- borrow_records：purpose、borrow_note、admin_comment、return_note
- duty_schedules：status
- users：phone

需要说明的是：这些字段不是为了发布而临时新增的功能，而是路由代码已经实际依赖的字段。这一阶段做的事情，是让全新 clone 之后执行初始化时，schema 与当前代码保持一致。

## 7. 第六阶段：Fresh Clone 可运行性

顺着上一阶段的问题，这一阶段的目标很明确：让代码离开原开发电脑之后，仍然能初始化出一个干净的本地数据库并运行起来。

具体做了两件事：

- 新增 `backend/scripts/init-db.js` 数据库初始化脚本
- `package.json` 增加 `npm run init-db` 命令

初始化脚本建立 7 张表：bind_codes、borrow_records、checkins、duty_schedules、materials、sessions、users。脚本设计为可重复执行：建表使用 IF NOT EXISTS；演示数据只在表为空时写入，不覆盖已有业务数据；绑定码只在通过环境变量显式配置时才创建对应记录。

验证方式是完整走一遍：`npm install` → `npm run init-db` → `npm start`，然后请求 `/api/health` 确认服务正常。这一步验证通过后，仓库才算具备了「clone 即可运行」的基础。

## 8. 第七阶段：GitHub 发布前脱敏

决定把项目放上 GitHub 之后，最重要的工作是脱敏。项目最初是直接面向实际运行环境开发的，发布前专门逐项检查并处理了这些内容：

- `.env`：不入库，只提供 `.env.example`
- `node_modules`：不入库
- SQLite 生产数据库：不入库（含全部业务数据）
- 日志、备份文件、私有配置：不入库
- 私钥 / SSH 相关文件：不入库
- 微信 AppSecret：改为环境变量读取，仓库中只有占位符
- 真实 OpenID：管理员白名单改为 `ADMIN_OPENIDS` 环境变量配置，不出现真实值
- Token / Session 数据：只存在于运行时数据库，不进仓库
- 生产服务器 IP / 生产域名：不出现，架构文档只描述抽象部署方式
- 管理员绑定码：不再提供默认值，改为 `ADMIN_BIND_CODE` / `STAFF_BIND_CODE` / `REVIEW_BIND_CODE` 环境变量配置

`backend/.env.example` 只保留环境变量名称和示例占位符：PORT、WECHAT_APPID、WECHAT_SECRET、ADMIN_OPENIDS、ADMIN_BIND_CODE、STAFF_BIND_CODE、REVIEW_BIND_CODE。

`.gitignore` 相应覆盖了：`.env` / `.env.*`（保留 `.env.example`）、`project.private.config.json`、`node_modules/`、`*.db` / `*.sqlite` / `data/`、各类密钥文件（pem / key / pfx / p12 / id_rsa 等）、日志与临时文件、备份文件。

此外登录日志不再输出完整 OpenID 与姓名，种子数据里的姓名也换成了明显的示例值。

> 说明：上述「绑定码环境变量化」「ADMIN_OPENIDS 环境变量化」「OpenID 日志脱敏」属于 GitHub 发布安全整理阶段的工作，当时尚未同步到生产环境；生产系统与 GitHub 发布版存在少量安全配置差异，后续单独评估生产同步。本文档不记录任何真实旧值。

## 15. 开发中遇到的问题

### 1. 数据库 schema 与 routes 不同步

问题：旧数据库因为字段是陆续补的，可以正常运行；但 fresh database 初始化后可能缺少当前路由代码实际在用的字段。

解决：发布整理时对照当前路由的实际查询和写入，逐列修正初始化 schema（borrow_records 的用途 / 备注 / 批注字段、duty_schedules 的 status、users 的 phone），并完整验证 fresh 初始化流程。

经验：数据库结构和代码需要同步维护；发布前做一次全新数据库的初始化验证很有必要。

### 2. 历史 Bind 页面成为死代码

问题：早期尝试的身份绑定页面仍留在项目中，但实际登录审核流程已经不使用它，而且它没有有效的导航入口，还依赖了已不存在的方法。

解决：GitHub 发布整理时确认其为死代码，在发布版中移除该页面及其注册，文档同步更新。最终发布版 5 个注册页面全部真实存在。

经验：长期开发后需要定期检查死页面和失效调用，避免残留代码误导后来的人。

### 3. 本地开发配置与生产配置混在一起

问题：项目最初主要面向实际运行环境开发，配置和代码没有严格分离，不适合直接公开。

解决：发布前把敏感配置全部迁移到环境变量（AppSecret、管理员 OpenID、绑定码等），公开仓库只保留 `.env.example` 示例值和占位地址，前端 AppID 改为 touristappid。

经验：配置与代码分离应该尽早进行，而不是等公开前集中处理。

### 4. 没有从项目第一天使用 Git

问题：早期开发历史无法通过 commit 直接展示，Git 历史只能从发布整理阶段开始。

解决：不伪造 commit，不 backdate；用 DEVELOPMENT_LOG 和 PROJECT_HISTORY 回顾真实开发过程，并对「哪些是确证、哪些是推断」做了明确标注。

经验：未来项目从第一天开始使用版本控制，最好配合有规律的 commit 习惯。
