# Development Log

> 说明：本文件是根据开发过程进行的回顾性整理。项目早期没有持续使用 Git 版本控制，Git commit history 从正式 GitHub 版本开始记录；本文不伪造过去的 commit 记录。

## 项目起因

学生会办公室 908 日常存在物资借用与人员值班两类管理需求。此前依赖人工登记，记录分散、查询和统计不便。为减少人工登记工作量、统一记录数据，决定开发一套小程序 + 后端的管理系统。

## 第一阶段：需求分析与 MVP

最初确定的核心需求：

- 物资管理：登记、库存、借用、归还
- 值班管理：排班、打卡
- 权限管理：管理员与工作人员

技术选型：

- 前端：微信小程序（原生 WXML / WXSS / JavaScript）
- 后端：Node.js + Express
- 数据库：SQLite（better-sqlite3）

## 第二阶段：物资管理

根据当前代码实现：

- 物资列表与详情查询
- 物资新增（编号唯一性校验）
- 物资编辑（总量、可借数量、状态等字段校验）
- 物资停用（软删除，保留历史数据）
- 库存字段（总量 / 可借数量）与状态字段（可借用 / 已借完 / 损坏 / 停用）
- 数据一致性规则：不可借状态强制可借数量为 0

## 第三阶段：借还流程

根据当前代码实现：

- 借用：事务内写入借还记录并扣减库存；借用前校验物资状态与库存
- 归还：事务内更新记录状态并恢复库存；校验归还后不超过总库存
- 记录查询：全部记录、未归还列表、最近记录、未归还统计
- 管理员批注接口

## 第四阶段：值班系统

根据当前代码实现：

- 值班排班新增、编辑、软删除
- 日期规范化（统一保存为 YYYY-MM-DD）
- 本周值班查询与统计
- 打卡：重复打卡校验、打卡人与值班安排中的人员一致性校验
- 打卡记录查询、统计与管理员删除（软删除）

## 第五阶段：微信用户体系

根据当前代码实现：

- 小程序端 wx.login 获取临时 code
- 后端调用微信 code2Session 换取 openid
- 用户表（users）记录微信身份、姓名、角色与状态
- 登录成功后服务端生成随机 Token，写入 sessions 表（7 天有效期）
- 新用户默认 pending 状态，等待管理员审核；active 用户可正常使用

> 历史说明：开发过程中曾尝试独立身份绑定页面，后续认证流程调整后，该未完成页面不再参与当前业务流程，因此未纳入 GitHub 发布版。

## 第六阶段：权限系统

根据当前代码实现：

- 全局中间件统一鉴权：除健康检查与微信登录外，接口均需有效 Token
- 角色：工作人员（staff）/ 管理员（admin）
- 管理员操作边界：物资 / 值班 / 打卡的写操作、用户管理、借还批注等
- 权限判断基于服务端 session 中的用户角色；早期实现曾依赖客户端提交的角色标记，后续改为服务端基于 session / role 判断，客户端字段仅作兼容保留

## 第七阶段：后端部署

生产环境采用的技术方式：

- Linux 服务器
- Node.js 运行后端
- PM2 进程管理
- SQLite 本地数据库
- HTTPS 反向代理对外提供 API
- 开发联调阶段曾使用本地 SSH 隧道访问后端

## 第八阶段：安全修复与回归

开发过程中逐步完善的安全处理：

- 全局登录鉴权（未登录 401）
- 管理员操作后端强制校验（staff 越权操作返回 403）
- 值班 / 打卡删除操作的服务端角色校验
- 绑定码机制与环境变量配置
- 敏感日志处理

> 注意：GitHub 发布版的「绑定码环境变量化」「ADMIN_OPENIDS 环境变量化」「OpenID 日志脱敏」属于「GitHub 发布安全整理」阶段的工作，当时尚未同步到生产环境。

## 第九阶段：GitHub 发布准备

为公开仓库进行的整理工作：

- 建立独立发布副本，与开发工作区分离
- 前端与后端源码脱敏（真实 OpenID、默认绑定码、敏感日志）
- 排除：`.env`、生产数据库、node_modules、私钥、日志、备份
- 增加：`.env.example`、`npm run init-db` 初始化脚本、安全默认配置
- 在发布版 fresh database 验证过程中发现初始化表结构与当前路由字段存在历史差异，因此同步补齐初始化 Schema

说明：生产系统与 GitHub 发布版存在少量安全配置差异，后续将单独评估生产同步。

## 当前状态

核心业务闭环已完成：物资登记与库存 → 借还与归还 → 值班排班与打卡 → 用户登录与权限审核。项目仍在持续维护中。
